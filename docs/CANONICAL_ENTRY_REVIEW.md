## Continuation — bounded JSON and regression reconciliation (2026-11-04)

* **IMPLEMENTED / TESTED (partial):** `parseBody` now reads at most 1 MiB from the request stream and, before Zod, rejects structures deeper than 32, arrays or objects with more than 1,000 items/properties, strings/keys longer than 65,536 UTF-16 code units, or more than 10,000 total value nodes. Guarded handlers map byte-limit failures to 413 and complexity failures to 422 with a generic error. A 100,000-item probe proves element validation did not start; production-server HTTP tests cover rejection and normal schema validation. Those fixed values require domain-owner review for legitimate larger records.

## Existing authority and new entry behavior

* Root on a control-plane or neutral host serves the public homepage. `/sign-in` uses the existing single form and `/api/v1/auth/login`; password verification, account and source limits, TOTP/recovery code handling, atomic session issuance, and session cookies remain the existing implementation. The form omits an empty MFA field, allowing the existing API to issue its MFA challenge. Locked and unknown identities now receive the same generic credential error; the lockout itself and its audit remain intact.
* A successful ordinary sign-in opens `/launcher`. It resolves persisted grants and scopes on the server: zero destinations produces a safe pending message; one enters its existing route; multiple displays only accessible destinations. Clicking an item is not authority: destination guards, RBAC/ABAC, tenant/entity/country/classification scope, RLS, step-up, and approvals remain in force. There is no invented role-to-workspace or default-workspace table. Foundation is a separate nonprofit organization; Family Office and NOELIA are shared surfaces, not additional Sector OSs.
* With a valid configured canonical apex and an exact registered destination hostname, an unauthenticated root, sign-in, or guarded entry request redirects to `https://www.<configured-apex>/sign-in?destination=<registry-code>`. That code is only a request: arbitrary paths, URLs, duplicate parameters and unregistered codes are ignored. After authentication the existing server resolver checks the requested destination; an unauthorized canonical entry renders a denial and appends `identity.destination.entry` with `DENIED` to the tenant-scoped audit ledger. An authorized request goes to the registry route, where the original guard rechecks. Exact deep-link paths are not retained: the continuation is the destination's registered root.
* Unknown, malformed, unconfigured and preview hosts never create cross-host redirects. A host cannot grant access. Existing authenticated destination-host sessions still use the existing guarded entry paths. Existing per-page/API authorization and audit behavior is unchanged; **not every direct page-level denial is newly audited by this change**.
* The session cookie remains host-only by default, HttpOnly, SameSite=Lax and Secure in production. Domain sharing is already an explicit opt-in only when the cookie domain equals the configured canonical apex; this change does not enable it. Without sharing, the www session opens authorized destinations on same-origin `/os/...` routes instead of bouncing to a host that cannot see the cookie. Separate pre-existing host-only sessions cannot be centrally revoked by clearing the www cookie. No cross-subdomain SSO is claimed.

## Security and availability limitations

* The Health mount requires the existing identity bridge and fails closed if its schema/service is unavailable. Its federated SPA/backend has a separate authentication integration; the BEYU session is not automatically bridged to a Health backend JWT. A seamless one-login Health journey remains blocked on that integration and operator configuration.
* Historically, direct Foundation denial paths raised `FoundationError` during concurrent rendering. The partial remediation and remaining 200-status blocker are described in the snapshot above.
* Some existing page-level denials do not write the new canonical-entry audit event; proving comprehensive denial auditing and evaluating audit-volume/rate-abuse behavior need follow-up. The new event is emitted only for authenticated requests denied at canonical sign-in.
* The dependency audit identified critical Next.js advisories in 16.3.8. This branch updates Next.js to 16.4.5. Zod has since been upgraded; see the current audit and compatibility caveats above.
* No conclusion about real DNS, TLS, Vercel/production environment variables, tenant assignments, external connectors, production authorization, availability, or actual production deployment can be drawn from these tests. A human must verify configuration and complete security review before any release.
